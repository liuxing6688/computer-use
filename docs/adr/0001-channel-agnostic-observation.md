# 观察接口与感知通道无关，一期只实现像素通道

**Status**: accepted

Windows 上感知界面有两条路：UI Automation 可及性树（精确、便宜、可文本化）和截图 + 视觉定位（通用、昂贵、依赖模型的坐标定位能力）。我们把二者统一在同一个观察接口后面——两者产出的都是"描述 + 边界框"的目标清单，形状同构——上层的作用域校验、执行前校验、危险动作判定因此只需实现一次。一期只实现像素通道。

## 为什么不是元素通道优先

调研显示元素通道在主流 Windows 应用上明显更可靠，我们原本也打算以它为主。推翻这个前提的是微信：4.1.13 是 Qt 5.15 自绘，整棵 UIA 树只有 2 个节点（窗口 + 一个名为 `MMUIRenderSubWindowHW` 的不透明渲染面，零子节点、零 pattern），窗口最小化或恢复都一样。这类应用无论元素通道做得多好都够不着，而它恰恰是最想要这个工具的那一类。

QQ NT 9.9.31 则相反。首轮探查给出的"渲染器可及性只被部分激活"是**窗口最小化造成的假象**——Chromium 在窗口最小化时抑制渲染器可及性。窗口恢复后重测为 429 个元素：会话列表条目各自可 Invoke 且带名称、时间、预览与未读数，消息气泡带发送者与正文，搜索框支持 ValuePattern，发送按钮可 Invoke 且禁用态直接体现在类名上，聊天头部的会话名可用于执行前校验。即元素通道在 Electron 应用上是完全可用的。

由此，选择像素通道的依据只剩一条：它是唯一能覆盖微信这类自绘应用的通道。知道 QQ 可用之后我们仍决定一期只做像素通道——理由不再是"元素通道用不了"，而是不愿在第一版同时调两条链路，分不清失败源自通道还是设计。元素通道二期接入，代价是 ADR-0003 那套补偿机制（模型自报 + OCR 抽查）在一期必须扛住全部判定责任。

## 为什么像素通道在这里可行

通用结论是通用视觉模型在高分辨率小目标上定位不可靠，且 API 会把截图长边压到 1568 px。我们绕开了这一点：截图**只截目标窗口**而非全屏（验收样本窗口约 1176×800 逻辑像素，125% 缩放下物理约 1470×1000，未触及上限，原尺寸送入模型），并提供区域放大动作应对小目标。

## 后果

- 模型只对它看见的那张截图的像素坐标负责，所有坐标换算留在服务端；服务端进程必须声明 `PER_MONITOR_AWARE_V2`，每张截图须携带窗口、时刻、缩放比与屏幕偏移。
- 元素通道日后接入时，必须实现为同一观察接口的另一个实现，而不是另一套工具。
- 实现约定：UIA 必须按 HWND 附着（`AutomationElement.FromHandle`）。从 `RootElement` 按进程过滤在两个样本上都只返回一个无子节点的壳。
