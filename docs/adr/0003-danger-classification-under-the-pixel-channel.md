# 像素通道下的危险动作判定：模型自报 + OCR 抽查

**Status**: accepted

有可及性树时，"这次点击落在名为『发送』的按钮上"是服务端可以自行判定的事实。像素通道下服务端只看到 `click(842, 1051)`，对坐标底下是什么一无所知——危险动作清单会因此变成空集。我们用两条互补的判据把它填回来：模型在调用时自报意图与危险性，服务端同时对点击坐标周围的小块区域做 OCR，命中高危词（删除、卸载、发送、确定、支付等）即判为危险。任一判据为真则拦截。模型自报不危险而 OCR 命中时，拦截方式是同一次调用里的原生对话框（ADR-0004）。

## 为什么两条都要

只靠模型自报，判定权就回到了模型手里：它判断错或被说服时拦截不会触发，此时所有安全设计都只是装饰。只靠 OCR 关键词则误报极多（"确定"到处都是），单独用会制造确认疲劳。两者取并集，代价是每次点击多几十毫秒——用 Windows 自带的 OCR API，只识别一个小区域，开销可以忽略。

## 同时生效的其它判据

- **命中测试**：点击前用 `WindowFromPoint` 确认坐标下的窗口属于任务作用域，否则拦截。这是"落到作用域外"这一类危险动作在像素通道下唯一可判定的形式。
- **截图比对**：动作须携带模型决策时那张截图的 ID；执行前重新采集，目标区域变化超阈值则拒绝并要求重新观察。界面在模型思考期间自行移动（新消息把列表顶下去一格）是纯视觉方案最典型的翻车方式。
- **限速与预算**：动作间强制间隔，连续输入动作超过阈值自动停下。真正的事故都来自"三秒内点了二十下"。
- **全局热键急停**：Agent 连续动作时会持续抢占前台焦点，人未必点得中 Agent 所在窗口去中止。

## 明确接受的风险

服务不设服务端启用闸门，"仅在用户显式调用 Skill 后才工作"是提示词层面的约定而非机制。由于 `SendInput` 只作用于前台窗口，模型在未被召唤时自行调用输入工具会直接抢走用户的焦点。急停与限速是这一选择的主要补偿。
